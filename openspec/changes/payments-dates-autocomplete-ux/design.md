## Context

Шесть независимых UX-фиксов в разных частях приложения, сгруппированные в один change
из-за общей темы «полировка форм ввода» и малого размера каждого пункта по отдельности.

Текущее состояние (по коду):
- `MandatoryPaymentsPage.tsx`: кнопка «Отменить» — отдельная `ghost`-кнопка рядом с
  бейджем «✓ Оплачено», видна всегда пока `isCurrentlyPaid(last_paid_at)` истинно.
  `isCurrentlyPaid = lastPaidAt != null` — это условие никогда не сбрасывается: при
  `MarkPaid` бэкенд одновременно продвигает `next_payment_date` на следующий период и
  выставляет `last_paid_at`, но ничто не очищает `last_paid_at`, когда наступает новый
  период. Платёж бессрочно выглядит «оплаченным».
- Дата вводится через нативный `<input type="date">` в 5 местах:
  `ProjectCreateSheet.tsx`, `MandatoryPaymentSheet.tsx`, `TransactionFormSheet.tsx`,
  `PlannedExpenseSheet.tsx`, `ModerationTable.tsx`. Формат отображения нативного инпута
  зависит от локали браузера/ОС, а не от `formatDate()` (`dd.mm.gg` через точку),
  которым уже пользуется таблица транзакций. `MandatoryPaymentsPage.tsx` также выводит
  `next_payment_date` сырой ISO-строкой (`YYYY-MM-DD`) в колонке таблицы, не через
  `formatDate()`.
- `TagFilterPicker.tsx` — кастомный dropdown с портал-рендерингом; максимальная высота
  меню жёстко задана `MAX_MENU_HEIGHT = 288` (соответствует `max-h-72`).
- Требование «Автодополнение наименования» уже присутствует в `specs/transactions/spec.md`
  (одна абстрактная сценария), но не реализовано ни на бэкенде, ни на фронтенде.
- `ExpensesCalendar.tsx` красит столбцы через Tailwind-классы на базе
  `bg-primary` / `bg-muted-foreground`; фиксированных фирменных hex-цветов нет.

## Goals / Non-Goals

**Goals:**
- Убрать структурный баг «вечно оплаченного» регулярного платежа и перенести действие
  отмены в меню
- Единый визуальный формат и способ ввода даты во всех формах
- Быстрый ввод суммы через арифметическое выражение прямо в поле «Сумма»
- Более просторное окно выбора категории
- Рабочее автодополнение наименования с автоподстановкой по истории проекта
- Фирменная палитра столбцов календаря расходов

**Non-Goals:**
- Полноценный виджет-калькулятор с кнопками/клавиатурой — реализуем как разбор
  арифметического выражения, введённого в текстовое поле
- Глобальная (между проектами/пользователями) статистика наименований
- История нескольких периодов оплаты регулярного платежа (мульти-период отмены)
- Изменение палитры где-либо, кроме столбцов `ExpensesCalendar`

## Decisions

### 1. Период-скоуп статуса «Оплачено» и перенос кнопки отмены

Вместо булева `last_paid_at != null` вычисляем `is_paid_current_period` на бэкенде:

```go
isPaidCurrentPeriod := p.LastPaidAt != nil && time.Now().Before(p.NextPaymentDate)
```

(`MarkPaid` уже продвигает `NextPaymentDate` на следующий период при оплате — как только
текущая дата достигает нового `NextPaymentDate`, платёж за прошедший период считается
«не оплачен за текущий период», а не «навсегда оплачен»). Поле добавляется в
`MandatoryPaymentResponse` как `is_paid_current_period: bool`; фронтенд использует его
вместо локального `isCurrentlyPaid()`. Вычисляется на сервере (не на клиенте), чтобы
избежать рассинхронизации часовых поясов клиента/сервера.

Кнопка «Отменить» убирается из колонки `paid` и добавляется как `DropdownMenuItem`
(деструктивный стиль) в существующее меню действий (`...`), рендерится только если
`is_paid_current_period === true`. Так как в системе хранится только один
`last_paid_at`/`last_transaction_id` на платёж (без истории периодов), «последний
совершённый платёж» — это и есть текущая запись; дополнительная модель данных не нужна.

### 2. Единый календарь-пикер дат

Новый компонент `src/components/ui/date-picker.tsx` на базе `react-day-picker` +
существующего `Popover` (shadcn-паттерн), с локалью `ru` (`date-fns/locale/ru`) и
отображением `dd.MM.yyyy` через точку. Наружу компонент сохраняет контракт
`value: string /* yyyy-MM-dd */`, `onChange: (v: string) => void` — так что замена
`<input type="date">` в 5 файлах становится drop-in заменой без изменений в
валидации/сбросе форм. Требуются новые зависимости `react-day-picker` + `date-fns`
(лёгкие, де-факто стандарт для shadcn-календарей, избавляют от ручной сетки дат).

`MandatoryPaymentsPage.tsx` — ячейка `next_payment_date` оборачивается в `formatDate()`.
Аудит: перед реализацией — grep по `\.date\b` / `next_payment_date` на предмет
оставшихся сырых ISO-выводов вне `formatDate()`.

### 3. Калькулятор в поле «Сумма»

Без отдельного UI-калькулятора: пользователь вводит выражение прямо в текстовое поле
(`378+567+844`), при потере фокуса (`onBlur`) или сохранении форма вычисляет результат
и заменяет значение поля на итог. Реализация — собственный безопасный разбор
арифметики (числа, `+ - * /`, скобки, `,`/`.` как разделитель дробной части) в
`src/lib/format.ts` (`evaluateAmountExpression`). **Явно не используем `eval`/
`new Function`** на пользовательском вводе — только whitelist-парсер. Если выражение
некорректно — поле остаётся как есть, показывается обычная ошибка валидации суммы
(как сейчас для нечисловых значений).

### 4. Высота окна выбора категории

`TagFilterPicker.tsx`: `MAX_MENU_HEIGHT` увеличивается с `288` до `~420` (константа),
существующая логика адаптивного позиционирования (обрезка по доступному месту сверху/
снизу от `recalc()`) не меняется — просто поднимается потолок.

### 5. Автодополнение наименования транзакции

В бэкенде уже существует `GET /api/v1/transactions/suggestions` →
`TransactionRepository.Suggestions` (`internal/repository/transaction_repo.go:168`),
но это упрощённый `SELECT DISTINCT title ... WHERE title ILIKE '%q%'` без
word-boundary матчинга и без данных для автозаполнения (только список строк).
Вместо отдельной таблицы статистики с инкрементальными счётчиками — переиспользуем и
расширяем этот же эндпоинт, вычисляя всё нужное **на лету агрегацией по существующей
таблице `transactions`**: так стата всегда синхронна с реальными данными (в отличие от
отдельного счётчика, который бы «протух» при редактировании/удалении транзакций), и не
нужна ни новая таблица, ни миграция, ни upsert-логика при сохранении.

Обновлённый `Suggestions` — вместо regex с POSIX-классом `[:alnum:]` (в Go-регэкспе он
ASCII-only и молча ломает word-boundary матчинг кириллицы — обнаружено юнит-тестом при
реализации), матчим слово-в-начале через явную разбивку по пробелам и `ILIKE`-префикс:
```sql
SELECT title, amount, tag_id, category, specificity, COUNT(*) AS cnt, MAX(date) AS last_used
FROM transactions
WHERE project_id = $1
  AND EXISTS (
    SELECT 1 FROM unnest(regexp_split_to_array(title, '\s+')) AS word
    WHERE word ILIKE $2 ESCAPE '\'
  )
GROUP BY title, amount, tag_id, category, specificity
```
где `$2` — `<escaped_q> || '%'`, экранированный от LIKE-спецсимволов (`\`, `%`, `_`) в
Go (`likePrefixPattern`) перед передачей как bind-параметр — иначе `%`/`_` в
пользовательском вводе вели бы себя как wildcard. Далее в Go-коде сервиса:
- группируем результат по `title`, для каждого наименования выбираем строку с
  максимальным `cnt` (при равенстве — с более поздним `last_used`)
- сортируем итоговый список наименований по алфавиту
- пустой `q` → пустой список (проверка на фронтенде и в сервисе, запрос к БД не
  выполняется)

Ответ эндпоинта расширяется с `[]string` до списка объектов
`{title, amount, tag_id, category, specificity}` — под новый контракт нужно обновить
и фронтенд-клиент (сейчас, если он уже использует `suggestions`, ожидает строки).

Фронтенд: в `TransactionFormSheet.tsx` поле «Наименование» получает debounce-запрос
(~250мс) при `title.length >= 1`, дропдаун с подсказками; выбор варианта заполняет
`amount`, `tagId`, `specificity` (остаются редактируемыми). Механику позиционирования
дропдауна (portal в ближайший `[role="dialog"]`, viewport-aware высота) переиспользуем
из `TagFilterPicker.tsx` — выносим в общий хук, чтобы не дублировать код.

### 6. Палитра столбцов календаря расходов

CSS-переменные в `src/index.css`:
```css
--bar-past: #C3C9D5;           --bar-past-hover: #8E98AB;
--bar-today: #E0C68F;          --bar-today-hover: #CBAD6B;
--bar-planned-bg: #FBF6EC;     --bar-planned-border: #E0C68F;
--bar-planned-hover-bg: #F4E9D2; --bar-planned-hover-border: #CBAD6B;
```
`ExpensesCalendar.tsx` вычисляет состояние столбца (`past` / `today` / `planned`) по
сравнению `item.key` (для `level=day`) или года+месяца (для `level=month`) с текущей
датой — API `CalendarItem` уже содержит `is_current`, дополнительно нужно только
сравнение "raньше/позже сегодня", без изменений бэкенда. Цвета применяются через
Tailwind arbitrary-value классы, привязанные к CSS-переменным
(`bg-[var(--bar-past)] hover:bg-[var(--bar-past-hover)]`), а не inline `style` — это
соответствует уже принятому в коде стилю (`bg-[hsl(var(--expense))]` в
`MandatoryPaymentsPage.tsx`). Для «планируемых» (будущих) дней — бледная заливка +
пунктирная рамка `1.5px dashed` вместо сплошной заливки. Радиус (`rounded-md`) и
фиксированная высота 6px для дней без данных (`has_data=false`) сохраняются как есть —
меняется только цвет/рамка, не геометрия.

## Risks / Trade-offs

- Смена семантики "оплачено" — поведенческое изменение (**BREAKING**): платежи,
  чей `next_payment_date` уже прошёл к моменту деплоя, при следующей загрузке страницы
  покажут «Оплатить» вместо «✓ Оплачено», даже если раньше выглядели оплаченными.
  Это ожидаемое исправление бага, но выглядит как заметное разовое изменение в UI —
  стоит явно упомянуть в релизных заметках.
- Замена `<input type="date">` на кастомный пикер в 5 разных формах — риск регрессии
  валидации/сброса в каждой; контракт `value`/`onChange` сохраняется намеренно, чтобы
  минимизировать изменения вокруг каждого поля.
- Поиск подсказок наименования через `unnest(regexp_split_to_array(...))` без индекса —
  приемлемо для объёма данных одного проекта (тысячи, не миллионы строк); при росте
  объёма можно добавить функциональный индекс или `pg_trgm` позже.
- Новая зависимость `react-day-picker` + `date-fns` — небольшой рост бандла; можно
  подключать `date-picker.tsx` лениво (`React.lazy`) там, где это не критично для
  первого рендера.

## Migration Plan

- Миграций не требуется: автодополнение считается агрегацией по существующей таблице
  `transactions`, период-скоуп статуса «Оплачено» вычисляется на лету без изменений
  схемы `mandatory_payments`, остальные пункты (дата-пикер, калькулятор, высота меню,
  палитра) — только фронтенд

## Open Questions

- Нужно ли фиксировать статистику наименований для транзакций, автосозданных через
  `MarkPaid` регулярных платежей, или только для транзакций, вручную сохранённых через
  форму «Новая транзакция»? Дизайн предполагает второе (у регулярного платежа
  наименование/сумма/тег и так фиксированы заранее).

## Context

Сейчас единственный аналитический виджет — `ExpensesCalendar` на `/transactions`
(бар-чарт по дням/месяцам, ручная Tailwind-вёрстка столбцов, без сторонней
чарт-библиотеки). Backend: `AnalyticsRepository` умеет только `SumByDayInMonth`,
`SumByMonthInYear`, `ListExpenseTransactionsInMonth`, `ExistsExpenseBefore` — все
фильтруют `category='expense'`, ни один не группирует по `specificity` или по дереву
тегов, ни один не работает с доходами. Таблица `spending_limits` существует в схеме
(`tag_id, amount, period_type, period_start, period_end`) с момента `000001_init_schema`,
но backend-кода для неё нет вообще — ни репозитория, ни хендлера. `mandatory_payments`
структурно описывает только исходящие платежи (нет поля категории доход/расход) —
это ограничивает прогноз баланса: будущий доход придётся оценивать по историческому
тренду, а не по явному расписанию.

## Goals / Non-Goals

**Goals:**
- Отдельная страница `/analytics` — полностью новый набор виджетов, календарь
  расходов на `/transactions` не трогаем
- Индекс свободы как флагманский, самый заметный виджет страницы, с симулятором
  «что если» и парным индикатором «жёсткости» бюджета
- Sankey доход → категория → подтег → остаток
- Прогноз баланса на 30/60/90 дней + прогноз даты накопления на товары из вишлиста
- Календарь по «настроению» трат и лента авто-инсайтов — «умный» слой поверх сырых
  чисел
- Сравнение текущего периода с прошлым/годом назад
- Рабочие лимиты трат (бюджеты) с прогресс-барами
- Всё новое строго изолировано на `/analytics`: ни одна существующая страница,
  компонент или файл вне `features/analytics/` не редактируется (кроме роута и
  пункта навигации), новые виджеты только читают чужие данные через уже
  существующие `GET`-эндпоинты

**Non-Goals:**
- Сравнение расходов между пользователями/участниками проекта
- Расписание будущих доходов как отдельная сущность (прогноз использует только тренд)
- Мультивалютность
- ML/LLM-генерация инсайтов — только детерминированные правила
- Редактирование вишлиста/регулярных платежей со страницы аналитики — только чтение
  и прогноз, сверх уже предусмотренного CRUD лимитов трат

## Decisions

### 1. Библиотека графиков — Recharts

Сравнение (уже прорабатывалось): **Recharts** (~150KB gzip, есть готовый `<Sankey>`,
SVG на React-компонентах — легко перекрашивается под уже существующие CSS-переменные
`--income`/`--expense`/`--primary`) vs **Nivo** (красивее «из коробки», но 500KB+ и
своя система тем, будет тереться с Tailwind) vs **Visx** (~80KB, но Sankey и линии
пришлось бы собирать самим на d3 — build all three chart types from primitives).
Recharts закрывает все три графика (Sankey, линия индекса свободы, линия прогноза)
одним пакетом с приемлемым весом; подключаем `AnalyticsPage` через `React.lazy`, чтобы
вес не бил по первому рендеру остального приложения.

### 2. Индекс свободы — новый агрегационный запрос

Метрика: `discretionary_share = SUM(amount WHERE specificity='simple') /
SUM(amount WHERE category='expense')` по месяцу. Новый метод
`AnalyticsRepository.FreedomIndexByMonth(ctx, monthsBack, projectID)`:
```sql
SELECT date_trunc('month', date) AS month,
       SUM(amount) FILTER (WHERE specificity = 'simple') AS simple_sum,
       SUM(amount) AS total_expense
FROM transactions
WHERE category = 'expense' AND project_id = $1 AND date >= $2
GROUP BY 1 ORDER BY 1
```
Отдаём `share = simple_sum / total_expense` за последние 12 месяцев (месяцы без
расходов — `share = null`, на графике — разрыв линии, а не 0%, чтобы не искажать
тренд). Эндпоинт `GET /api/v1/analytics/freedom-index?months=12`.

### 3. Sankey — узлы и агрегация

```
Зарплата ──┐
Фриланс ───┼──► [Доходы] ──┬──► Еда ──┬──► Кафе
                            │          └──► Продукты
                            ├──► Жильё
                            └──► Остаток / Накопления
```
Узел «Остаток» = `SUM(income) − SUM(expense)` за период; если отрицательный —
узел не рисуется (дефицит не выразить как поток в Sankey), вместо этого над диаграммой
текстовое предупреждение «Расходы превысили доходы на N ₽». Подтег сворачивается в
родительский тег для верхнего уровня узлов расходов, аналогично уже существующей
логике в `CalendarDayPopup` (свёртка подтега к тегу верхнего уровня). Один SQL-запрос
с `GROUP BY category, tag_id` за период + маппинг `tag_id → parent_id` в Go (тот же
паттерн, что и в `TagService.TagWithParent`). Эндпоинт
`GET /api/v1/analytics/income-expense-sankey?period=month&year=&month=`.

### 4. Прогноз баланса — три источника

```
Баланс, ₽
   │                            ┌╌╌╌╌╌ прогноз (пунктир)
   │        ___/\__/\___╱‾‾‾‾‾╱
   │  ______/                факт (сплошная)
   │_/
   └──────────────────────────────────────────► время
```
`forecast(t) = balance_today + income_trend(t) − mandatory_payments_projected(t) −
discretionary_trend(t)`, где:
- `mandatory_payments_projected` — детерминированная проекция вперёд по
  `recurrence`/`next_payment_date` (переиспользуем `advanceDate` из
  `mandatory_payment_service.go`)
- `income_trend`/`discretionary_trend` — среднедневная историческая ставка за последние
  90 дней (`AVG(amount)/90`), т.к. `mandatory_payments` не описывает доход, а
  «простые» траты по определению нерегулярны
- Обязательные платежи не дублируются в `discretionary_trend`, так как их
  исторические транзакции всегда `specificity='required'`, а тренд считается только
  по `specificity='simple'`
Если прогноз пересекает 0 — фронтенд подсвечивает точку пересечения и дату.
Эндпоинт `GET /api/v1/analytics/balance-forecast?days=30`.

### 5. Лимиты трат — реализация с нуля поверх существующей таблицы

`spending_limits.amount` — `NUMERIC(15,2)` (рубли) с исходной схемы
`000001_init_schema`; в отличие от `transactions`/`user_balance` (мигрированы на
`BIGINT`-копейки в `000002_add_tag_color_and_kopecks`) и `mandatory_payments`
(изначально `BIGINT` в `000008`), эту таблицу тогда забыли перевести. Приводим к
общему знаменателю: новая миграция `ALTER TABLE spending_limits ADD COLUMN
amount_kopecks BIGINT; UPDATE ... SET amount_kopecks = (amount * 100)::BIGINT; ALTER
TABLE spending_limits DROP COLUMN amount; ALTER TABLE spending_limits RENAME COLUMN
amount_kopecks TO amount;` — тот же паттерн, что и в `000002`.

Backend полностью отсутствует. Добавляем: `SpendingLimitRepository`
(CRUD + `SumSpentByLimit` — сумма транзакций по `tag_id` в пределах
`period_start`/`period_end` или текущего календарного месяца/недели при
`period_type IN ('month','week')`), `SpendingLimitService`, `SpendingLimitHandler`,
роут `/api/v1/spending-limits`. UI — панель на `/analytics` со списком лимитов и
прогресс-барами (`факт/лимит`, красная подсветка при превышении — переиспользуем
паттерн подсветки из `getDateHighlight`/просроченных `mandatory-payments`).

### 6. Календарь расходов остаётся на `/transactions`

Никакого переноса — `ExpensesCalendar.tsx` и `TransactionsPage.tsx` не
редактируются этим change вообще. `/analytics` — полностью новая страница со
своим набором виджетов; связь с обычным календарём расходов — только смысловая
(через новый `spending-mood-calendar`, независимый компонент), не структурная.

### 7. Общий селектор периода на странице аналитики

Индекс свободы всегда за 12 месяцев (фиксировано, не настраивается — это тренд, а
не срез). Sankey, календарь по «настроению» трат и сравнение периодов —
самостоятельные новые компоненты этого change, поэтому они свободно делят один
`year`/`month` state на уровне `AnalyticsPage` без риска задеть существующий код
(в отличие от переиспользования пикера из уже существующего `ExpensesCalendar`,
как планировалось раньше). Прогноз баланса — независимый селектор горизонта
(30/60/90 дней), не завязан на период остальных виджетов.

### 8. Индекс свободы — слайдер-симулятор «что если»

Чистый клиентский расчёт, без нового эндпоинта: у `FreedomIndexChart` уже есть
текущая доля `share` и абсолютная сумма «простых» трат за последний полный месяц.
Слайдер двигает целевую долю (0–100%), под ним — `projected_savings =
(current_simple_amount − target_simple_amount) × 12`, где `target_simple_amount =
target_share × total_expense_last_month`. Никакого нового API — вычисление в
`FreedomIndexChart.tsx` на уже загруженных данных.

### 9. Коэффициент «жёсткости» бюджета

Метрика: `fixed_cost_ratio = SUM(mandatory_payments.amount, спроецированные в
текущем месяце) / SUM(transactions.amount WHERE category='income' за месяц)`.
Переиспользуем `mandatory_payments` (список активных платежей, без пагинации — их
всегда немного) и уже посчитанную в прогнозе агрегацию дохода за месяц. Новый метод
`AnalyticsRepository.MonthlyIncome(ctx, year, month, projectID) (int64, error)` +
сумма `mandatory_payments.amount` из уже загруженного списка (без нового SQL —
берём из `MandatoryPaymentRepository.List`, суммируем в сервисе). Эндпоинт
`GET /api/v1/analytics/fixed-cost-ratio?year=&month=`, отображается компактной
цифрой/мини-баром рядом с индексом свободы (не отдельный большой график).

### 10. «Когда я смогу купить X?» — savings-goal-forecast

Только читает `planned_expenses` через уже существующий
`PlannedExpenseRepository.List` (не модифицируется) и переиспользует ту же
`income_trend − discretionary_trend − mandatory_payments_projected` дневную ставку
накопления, что и `balance-forecast` (Decision 4). Для каждого активного товара с
`cost_kopecks != null`: `days_needed = ceil((cost_kopecks − current_balance) /
daily_savings_rate)` (если `daily_savings_rate <= 0` — «неизвестно», а не
бесконечная/отрицательная дата). Отдельный сервисный метод
`AnalyticsService.GetSavingsGoals(ctx, projectID)`, переиспользующий приватную
функцию расчёта дневной ставки из `balance-forecast`. Эндпоинт
`GET /api/v1/analytics/savings-goals`, отдаёт по одному прогнозу на каждый товар
вишлиста (уже отсортированные по приоритету — как в существующем `planned_expenses`).

### 11. Календарь по «настроению» трат — новый отдельный компонент

Чтобы не трогать уже собранный и оттестированный `ExpensesCalendar.tsx`,
«настроенческий» календарь — **новый** компонент `SpendingMoodCalendar.tsx` со
своей копией сетки дней (тот же визуальный паттерн — колонка на день, но без
попапа/клика/уровней месяц-год, сильно проще оригинала). Данные — новый эндпоинт
`GET /api/v1/analytics/spending-mood-calendar?year=&month=`, переиспользующий
почти тот же SQL, что и `freedom-index`, но с группировкой по дню, а не по месяцу.
Цвет дня — `hsl` интерполяция между `--income`-зелёным (0% simple) и
`--expense`-красным (100% simple) по значению `share` дня; дни без расходов —
нейтральный `--muted`.

### 12. Умная лента инсайтов — правила, не ML

Никакого ML/LLM — набор детерминированных SQL-правил, вычисляемых при каждом
открытии страницы (без сохранения истории «прочитанных» инсайтов в v1):
1. Тег с наибольшим ростом расходов месяц-к-месяцу (`ABS(delta) > 20%`, минимум
   1000 ₽ дельты, чтобы не шуметь на мелких тегах)
2. Самая крупная транзакция-расход месяца
3. Тег, впервые встретившийся в текущем месяце (не было расходов по нему раньше)
Каждое правило — отдельная функция в `AnalyticsService`, возвращающая `*Insight`
(`nil`, если правило не сработало). Эндпоинт `GET /api/v1/analytics/insights`
отдаёт массив из тех правил, что сработали (0–3 элемента), с готовым текстом на
русском (форматирование текста — на бэкенде, не на фронтенде, чтобы не дублировать
логику склонения/чисел в двух местах).

### 13. Сравнение периодов

Переиспользуем существующий `AnalyticsRepository.ListExpenseTransactionsInMonth`-
подобный агрегат: новый метод `SumByTagForTwoPeriods(ctx, periodA, periodB
[from,to]time.Time, projectID) (map[tagID]{amountA, amountB int64}, error)` — один
запрос с `CASE WHEN date BETWEEN ... THEN 'a' ELSE 'b' END` группировкой, а не два
отдельных похода в БД. Топ-5 тегов берутся по `MAX(amountA, amountB)`. Эндпоинт
`GET /api/v1/analytics/period-comparison?mode=prev_month|prev_year`.

## Risks / Trade-offs

- Прогноз баланса — наименее точный виджет (тренд по историческим средним, не
  реальное расписание доходов); это первая версия, точность будет расти по мере
  накопления истории. Явно маркируем как «оценка», а не гарантию.
- Recharts — новая зависимость ~150KB; митигируется ленивой загрузкой страницы.
- Sankey с узлом «Остаток» при дефиците не показывает отрицательный поток —
  ограничение самой визуализации Sankey (потоки не могут быть отрицательными),
  решается текстовым предупреждением рядом с графиком.
- `savings-goal-forecast` наследует неточность `balance-forecast` (тренд по
  историческим средним) — при отрицательной или нулевой дневной ставке накопления
  показываем «неизвестно», а не вводящую в заблуждение дату/бесконечность.
- Правила `spending-insights` могут шуметь на аккаунтах с малой историей
  (1-2 месяца данных) — пороги (20% дельты, минимум 1000 ₽) подобраны, чтобы
  не показывать инсайты вообще, если данных недостаточно, а не показывать
  недостоверные.
- `SpendingMoodCalendar` дублирует часть вёрстки `ExpensesCalendar` (сетка дней) —
  осознанный trade-off в пользу изоляции: не трогаем существующий, оттестированный
  компонент ради одного нового режима отображения.

## Migration Plan

- Одна миграция: перевод `spending_limits.amount` с `NUMERIC(15,2)` на `BIGINT`
  (копейки) — см. Decision 5. Таблица уже существует, новых таблиц не требуется.
- Остальные аналитические эндпоинты (индекс свободы, Sankey, прогноз) — только
  агрегации по существующим `transactions`/`mandatory_payments`, без изменения схемы

## Open Questions

- Нужен ли отдельный порог для «резкого» индекса свободы (например, предупреждение
  если доля «по желанию» выросла > X п.п. за месяц)? Не включено в v1 — можно
  добавить отдельным небольшим изменением после того, как накопится история для
  калибровки порога.

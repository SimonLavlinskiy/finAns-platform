## Context

`ExpensesCalendar.tsx` (день-уровень) уже красит столбцы по состоянию
past/today/planned (см. `getBarState`, введено в `payments-dates-autocomplete-ux`) и
открывает попап (`CalendarDayPopup`) только для дней с `has_data=true` — будущие дни
без фактических транзакций сейчас никак не выделяются и не реагируют на наведение.
Компонент не знает о регулярных платежах вообще.

`MandatoryPaymentService.MarkPaid` (backend) сейчас: создаёт транзакцию с
`Date: p.NextPaymentDate` (запланированная дата), продвигает `NextPaymentDate` через
`advanceDate` и сохраняет `last_paid_at`. Фронтенд (`MandatoryPaymentsPage.tsx`) вызывает
`markMandatoryPaymentPaid(id)` без какого-либо тела запроса и без промежуточного
подтверждения — один клик сразу создаёт транзакцию.

Шрифты (Comfortaa, Nunito) сейчас подключены в `index.html` через
`fonts.googleapis.com/css2?family=...`. Локальные файлы уже скачаны в
`workspace/finAns-frontend/fonts/Comfortaa,Nunito/{Comfortaa,Nunito}/` — вариативные
TTF (`*-VariableFont_wght.ttf`) плюс статичные веса и italic-версии Nunito.

## Goals / Non-Goals

**Goals:**
- Будущий день с регулярным платежом визуально отличим от обычного «планируемого» дня
  и показывает платёж при наведении, но только пока день не наступил
- Оплата регулярного платежа проходит через попап подтверждения с редактируемой суммой
- Дата созданной транзакции — фактическая дата подтверждения, а не запланированная
- Шрифты грузятся с собственного домена, без обращения к Google Fonts

**Non-Goals:**
- Изменение алгоритма продвижения `next_payment_date`
- Подсветка регулярных платежей в годовом виде календаря
- Редактирование тега/наименования/периодичности в попапе подтверждения оплаты

## Decisions

### 1. Подсветка регулярного платежа — на фронтенде, без нового API

`ExpensesCalendar.tsx` уже вызывается на странице «Операции»; регулярных платежей в
проекте всегда немного (список без пагинации, см. `MandatoryPaymentsPage`), поэтому
достаточно дозагрузить `fetchMandatoryPayments()` тем же `useQuery` и построить
`Map<string /* YYYY-MM-DD */, MandatoryPayment>` по `next_payment_date` активных
платежей. Новый эндпоинт не нужен.

Правило подсветки для дня в текущем месячном виде:
```
isUpcomingPayment = date(day) > today && mandatoryPaymentsByDate.has(day.key)
```
(строго "больше сегодня" — как только день наступил, `next_payment_date` этого платежа
на бэкенде уже либо остался прежним, если не оплачен, либо продвинулся вперёд при
оплате; в обоих случаях для СЕГОДНЯШНЕГО и прошедших дней подсветка не нужна по
требованию — используем тот же `barState !== "planned"` водораздел, что уже есть).

Новое визуальное состояние `planned-mandatory` (только когда `barState === "planned"`):
заливка `--bar-planned-bg` (как обычный planned) + сплошная (не пунктирная) рамка
акцентного цвета, чтобы отличаться от обычных планируемых дней с той же пунктирной
рамкой. Ховер на такой день (даже при `has_data=false`) открывает мини-попап с
названием и суммой платежа — упрощённая версия `CalendarDayPopup`, не полноценный
разбор по тегам/транзакциям (которых для будущего дня физически ещё нет).

### 2. Попап подтверждения оплаты — переиспользование паттерна формы транзакции

Новый компонент `MarkPaidConfirmSheet` (по образцу `TransactionFormSheet`/
`MandatoryPaymentSheet`): при открытии предзаполняется `amount` из
`payment.amount`, показывает наименование и тег как read-only контекст (не
редактируются — см. Non-Goals), поле суммы — обычный `Input` с
`parseRublesInput`, как и в остальных формах приложения. Кнопка «Оплатить» на
`MandatoryPaymentsPage.tsx` больше не вызывает мутацию напрямую, а открывает этот
попап; сама мутация вызывается только по подтверждению внутри попапа.

### 3. Дата транзакции — вычисляется на бэкенде, не передаётся с фронтенда

`MarkPaid` меняется: транзакция создаётся с `Date: time.Now()` (сервер), а не
`p.NextPaymentDate`. Дата не принимается как параметр от клиента — сервер сам знает
текущий момент, это исключает рассинхронизацию часовых поясов клиент/сервер (тот же
принцип, что уже применялся для `is_paid_current_period` в предыдущем change).
`advanceDate(p.NextPaymentDate, p.Recurrence)` остаётся без изменений — новая дата
следующего платежа по-прежнему считается от старой запланированной даты, а не от
фактической даты оплаты.

Сумма — добавляется необязательное поле `amount` в тело `POST
/mandatory-payments/:id/mark-paid` (`dto.MarkPaidRequest{Amount *int64}`); если не
передано или `<= 0` — используется `p.Amount` как и раньше. Изменённая сумма
используется только для созданной транзакции; сумма самого регулярного платежа
(`mandatory_payments.amount`) не меняется — при следующей оплате снова предлагается
исходная сумма платежа.

### 4. Локальные шрифты — вариативные TTF через `@font-face`

Копируем только вариативные файлы (не все 20+ статичных весов) в
`src/assets/fonts/`: `Comfortaa-VariableFont_wght.ttf`, `Nunito-VariableFont_wght.ttf`,
`Nunito-Italic-VariableFont_wght.ttf` — три файла вместо полного набора статичных
начертаний, вариативный шрифт поддерживает весь диапазон весов (300–700) одним файлом.
`@font-face` с `font-weight: 300 700` (диапазон) в `src/index.css`, `font-display:
swap` (совпадает с поведением текущего Google Fonts подключения). Убираем
`<link rel="preconnect" href="https://fonts.googleapis.com">` и сам `<link
rel="stylesheet">` из `index.html`.

## Risks / Trade-offs

- Подсветка регулярного платежа только по совпадению `next_payment_date` — если у
  пользователя два регулярных платежа с одинаковой датой, попап покажет оба списком
  (не first-match), это ожидаемо и не считается edge-case багом.
- Убираем возможность backdate/forward-date платежа через сам попап оплаты — дата
  всегда «сейчас»; если нужно внести оплату задним числом, это делается как обычно
  через редактирование созданной транзакции на странице «Операции» после факта.
- Файлы шрифтов (`.ttf`) увеличивают финальный бандл на ~100-150KB суммарно
  (вариативные шрифты компактнее статичных наборов, но всё ещё не бесплатны) — приемлемо
  ради убирания внешнего запроса к Google Fonts (потенциальный privacy/perf выигрыш:
  один RTT меньше, независимость от доступности стороннего CDN).

## Migration Plan

- Миграций не требуется — `MarkPaid` не меняет схему, только источник даты и опциональный
  параметр суммы в теле запроса.
